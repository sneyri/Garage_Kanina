# ГАРАЖ КАНИНА — Техническое задание

## 1. Про что игра
- ГАРАЖ КАНИНА: бытовой психологический хоррор. Игра не должна пугать скримерами, а должна заставлять игрока испытывать дискомфорт.

## 2. Игровой цикл
- 1 цикл = 1 день. Каждый день игрок выполняет определённую работу по гаражу. Всего 7 дней.

## 3. Персонажи
- Главный герой: Никита.
- Владелец гаража и друг главного героя: Максим Канин.

## 4. В чём интерес
- Интерес в бытовой работе в гараже. Игра не должна быть «пойди туда, нажми кнопку, вернись». Каждое задание — мини-игра.
- При этом игра не должна состоять из одних мини-игр: бытовуха никуда не девается.

## 5. В чём страх
- Страх начинается с нарушения безопасности.
- На 2 день Максим доверяет работу Никите и в начале каждого дня уходит по делам. Он не курирует игрока всё это время.
- Сначала точка безопасности — гараж. Во время работы вне гаража игрок что-то чувствует, единственное место спасения — гараж.
- Рано или поздно гараж тоже перестаёт быть безопасным: в подполе гаража «оно» следит за игроком.

## 7. Архитектура и технические ограничения
- Стек: HTML, CSS, vanilla JS, Three.js.
- Запуск: только через `file://` двойным кликом по `index.html`. Никаких серверов, сборщиков, npm на стороне игры.
- Следствия `file://`:
  - ES-модули (`type="module"`) и `fetch`/`GLTFLoader` для `.glb` блокируются CORS. Использовать обычные `<script>` в нужном порядке и глобальный неймспейс (например `window.Game`).
  - Three.js лежит локально в папке проекта (не CDN), версия фиксируется.
  - 3D-модели встраивать в JS (base64 / JS-модуль с данными) или генерировать кодом.
- Хранение: localStorage + cookie (дублирование). Любой доступ в try/catch, игра работает и без хранилища.
- Браузеры: все основные (Chrome, Firefox, Edge, Safari). Не использовать экспериментальные API без запасного варианта.
- Структура кода в стиле NestJS: модули (gameplay, audio, ui, world, save), сервисы с одной ответственностью, слои не смешивать, связь между модулями через явные интерфейсы/события. Без «всё в одном файле».
- Управление: уточнить у пользователя (по умолчанию WASD + мышь, E — взаимодействие).

## 8. Определение «готово»
- Работа открывается по `file://` без ошибок в консоли.
- Работает в Chrome и Firefox минимум.
- Отчёт агента лежит в `Agents/` (см. раздел 9).
- Изменения закоммичены (см. раздел 10), если пользователь разрешил.
- Первая цель (MVP): дни 1–2 играбельны.

## 9. AGENTS — правила для агентов

### Модели
- Архитектура и механики: Opus 5.5, средний уровень мышления.
- 3D-модели и свет: сначала проверить доступ к Blender и работать в нём. Выбор модели:
  - Sonnet: маленькие модели, мелкие правки существующей модели.
  - Opus: создание карты, сложные модели, точечная работа со светом.
- Работа с имеющимися механиками и мелкие доработки: Sonnet.

### Перед работой
1. Проверить папку `Agents/` (нет — создать).
2. Прочитать `Agents/BASE.md` и все markdown-файлы своей области.
3. Если область не описана или неясно, что делать — спросить пользователя, не придумывать.

### Во время работы
- Править только файлы своей области. Чужие файлы не трогать, если не сказано в задании.
- Удалять файлы только если это прямо разрешено в задании.
- Решать самому: мелкие детали реализации. Спрашивать пользователя: содержание дней, сюжет, установка скиллов, удаление файлов, любые действия с GitHub.

### После работы
- Создать markdown-отчёт: что реализовано, как, какой агент.
- Имя файла: `agentName_modelName_workName.md`.
- Отчёты лежат в папках по областям внутри `Agents/`. Допустимые папки (новые не плодить, нужна новая — спросить):
  `Architecture`, `Gameplay`, `Models3D`, `Lighting`, `SoundDesign`, `UI`, `Story`.
- Отчёты пишутся полным подробным языком (caveman на них не распространяется).

### BASE.md
- Единственный файл в корне `Agents/`. Создаёт только главный агент (сессия, в которой пользователь ставит задачу) при создании игры. Содержит общую информацию о проекте.

### Скиллы
- Если скилл мог бы улучшить работу — уведомить пользователя: какой скилл и что делает. Без ведома пользователя никакие скиллы не устанавливать.

### Токены (САМОЕ ГЛАВНОЕ)
- Не тратить токены на ненужную работу.
- В чате использовать skill caveman на максимальном уровне: самые краткие ответы о проделанной работе.
- Развёрнутая информация — только в markdown-файлах в `Agents/`.

## 10. Git и GitHub
- Git установлен у пользователя. Репозиторий проекта лежит в корне папки игры.
- Без разрешения пользователя агент НЕ делает: `git push`, создание/удаление репозитория на GitHub, смену видимости, force-push, удаление веток, правку чужих коммитов.
- Локально можно (без вопроса): `git status`, `git diff`, `git log`, `git add`.
- Коммит — только по просьбе пользователя или после завершённой работы с вопросом «закоммитить?».
- Формат сообщения коммита: `область: что сделано` (пример: `gameplay: мини-игра замены колеса`). Один коммит = одна завершённая работа.
- Ветки: `main` — рабочая версия. Для крупных работ — отдельная ветка `область/название`.
- Перед крупным заданием с несколькими агентами — коммит текущего состояния как точка отката.
- В репозиторий не попадают: временные файлы, скриншоты отладки, `node_modules`, личные данные (см. `.gitignore`).
- GitHub-репозиторий: создаётся только после подтверждения пользователя (имя, приватный/публичный).
